# Fieldnotes v0.1 scope

## Status and interpretation

This document is the normative product scope for the Fieldnotes 0.1 release
line. It turns the broader product specification into incremental, testable
delivery boundaries.

In this document:

- **must** marks a requirement for the named release increment;
- **should** marks a strongly preferred behavior that may be adjusted from
  implementation evidence without changing the product boundary;
- **direction** describes intended future work and is not an external contract.

The 0.1 line is complete when the required capabilities through `0.1.9` are
delivered. A capability assigned to a later 0.1.x increment is not required for
an earlier increment. Patch numbering may change during release engineering,
but the dependency order and gates below remain the roadmap.

## Scope of the complete 0.1 line

The complete 0.1 line must provide:

- a native Rust command-line application with no required daemon, server, or
  Fieldnotes account;
- initialization of a portable Markdown notebook with a stable instance ID;
- the built-in `self` Field for typed Notes and imported files and voice
  recordings;
- first-party read-only Fields for local reference material, Outlook Mail,
  Outlook Calendar, Outlook Contacts, Microsoft Teams, and Jira;
- stable Field IDs, incremental collection, cursor safety, deterministic
  reconciliation, and visible diagnostics;
- flat, sparse, validated frontmatter and collision-safe global record IDs;
- retained, content-addressed artifacts sufficient to keep imported voice Notes
  playable and imported user material locally attributable;
- deterministic hashing, identity resolution, entity and relationship
  derivation, inspection, explanation, and rebuild;
- safe copying and merging of notebooks from different Fieldnotes instances;
- OS secure credential storage by default, with no credentials in notebook
  files, command-line arguments, logs, or cursor data;
- optional, user-enabled built-in enhancement that is disabled by default and
  delivered later in the 0.1 line;
- vendor-neutral proposal and handback-package preparation that never performs
  a destination write;
- usable output for plain-text tools and Obsidian without requiring Obsidian.

External-source Notes represent useful source state, not an immutable source
history. A Field refresh must reconcile a known source identity deterministically
and must not create uncontrolled duplicates. The precise on-disk update
mechanism belongs in the notebook and Field protocol specifications; it must not
claim evidence-ledger or compliance semantics.

## Release increments

The detailed requirements and gates are normative in the
[release roadmap](roadmap.md). The dependency-ordered release promises are:

- **0.1.0 — local notebook kernel:** initialization, `self`, text/file/voice
  import, artifacts, validation, and exact format fixtures. Voice remains
  useful without transcription.
- **0.1.1 — Field protocol and local Field:** child-process collection,
  checkpoint recovery, current-state reconciliation, a fixture Field, and the
  connector conformance kit.
- **0.1.2 — deterministic graph, rebuild, and merge:** scoped identities,
  entities, relationships, portable-source deduplication, conflicts, and
  disposable derived state.
- **0.1.3 — authentication and Outlook Mail:** OS credential providers,
  protected credential delivery, shared Microsoft Graph support, and
  incremental mail collection.
- **0.1.4 — Calendar and Contacts:** separately configured read-only Fields
  sharing Microsoft transport while retaining distinct prefixes and cursors.
- **0.1.5 — Microsoft Teams:** the explicitly approved and testable message,
  reply, participant, meeting-reference, and attachment slices, with clear
  permission and unavailable-history diagnostics.
- **0.1.6 — Jira:** read-only ticket and activity collection proving that the
  Field contract is not Microsoft-specific.
- **0.1.7 — artifacts, lifecycle, proposals, handback, and Obsidian:** approved
  renderers, safe archive/prune operations, vendor-neutral proposals, a
  portable handback package and manifest, notebook guidance, and Bases.
- **0.1.8 — optional built-in enhancement:** a release-paired engine providing
  voice transcription, bounded text Extractions, and cited Observations. It is
  optional to enable but required for this release increment, with no BYO model
  surface.
- **0.1.9 — release closure:** six target builds, packaging, security and
  license review, soak testing, complete documentation, and acceptance
  traceability.

GitHub is not part of the 0.1 roadmap.

## Cross-cutting acceptance gates

Every release increment must preserve the gates established by earlier
increments.

### Portability

- A Note must remain understandable from its Markdown body and flat frontmatter
  after being copied outside its original notebook.
- Shared properties must retain one meaning and type throughout a notebook.
- Source-specific properties must use the owning Field's prefix.
- Notebook use must not depend on a proprietary database or Obsidian.

### Safety and repeatability

- Valid-looking partial Notes must not remain after interrupted writes.
- A replay from the last committed checkpoint must reconcile known source
  objects rather than multiply them.
- Same-content artifacts may be reused without collapsing Notes that have
  different source context.
- Damage, truncation, skipped content, and conflicts must be visible.

### Provenance and merge

- Every Note must identify its Fieldnotes instance and Field.
- Notes from distinct instances must be copyable into one notebook without ID
  collisions or loss of producer identity.
- Matching portable `(source_scope, source_identity)` keys must deduplicate one
  upstream object exactly when current content agrees, while retaining all
  producer references.
- A divergent file bearing the same global Note ID must be preserved as a
  visible conflict, not silently overwritten.

### Deterministic graph

- Exact identity matching and derived edges must cite source Notes or a
  versioned deterministic rule.
- Weak identifiers such as display names must not silently merge entities.
- Deleting disposable indexes and rebuilding from notebook files and non-secret
  configuration must reproduce the same semantic graph.

### Credentials and privacy

- OS secure storage is the default credential provider.
- Plaintext credential storage must never be a silent fallback.
- Test fixtures must cover credential-like values in errors, URLs, process
  arguments, diagnostics, and cursors.

### Disposable workflow

- Fieldnotes must not claim that the notebook is an immutable archive or the
  sole durable copy of external-source state.
- A user must be able to inspect and process notebook files with ordinary tools
  before pruning or discarding them.
- No deletion or archive operation may require coordination with a Fieldnotes
  service.

## Product direction outside the normative 0.1 scope

The following directions explain where the product may go, but are not promised
interfaces or acceptance criteria for the 0.1 line:

- delivering a prepared package to a destination system or calling its APIs;
- helping a human or external AI translate reviewed material into a CRM,
  ticketing, task, knowledge, time-tracking, or other system workflow;
- richer archive and retention policies, including dependency-aware pruning of
  shared artifacts;
- direct microphone recording rather than import of an existing audio file;
- additional Fields, including GitHub;
- broader enhancement capabilities, languages, or resource profiles.

These directions do not authorize Fieldnotes to write to external systems and
do not define a destination API payload, approval protocol, or external
execution contract. The v0.1 handback manifest is a portable preparation
format, not a vendor request payload.

## Explicit non-goals for the 0.1 line

The 0.1 line does not include:

- writeback to any Field or other external system;
- immutable capture of every source revision or deletion;
- compliance retention, legal hold, audit-log, or evidence-ledger semantics;
- hosted synchronization, a Fieldnotes account, or a required daemon;
- arbitrary third-party connector loading as a general plugin marketplace;
- user-selected inference providers, endpoints, prompts, or models;
- sentiment, relationship-strength, importance, customer-health, personality,
  or intent judgments;
- GitHub collection;
- automatic delivery or application of downstream processing packages.
